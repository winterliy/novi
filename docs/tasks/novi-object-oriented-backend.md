# Novi 객체지향 컴파일러·인터프리터 백엔드 작업

## 목표

Novi의 문법과 사용자 기능은 사용자가 설계하고, 구현은 C++로 진행한다. 이 작업의 목표는 문법이 바뀌어도 재사용할 수 있는 **객체지향 언어 백엔드**를 단계적으로 만드는 것이다. 백엔드는 소스 코드를 분석하고, 오류를 진단하며, 프로그램을 컴파일하고 실행한다.

Novi 문법의 세부 표기와 의미는 이 문서에서 확정하지 않는다. 문법을 추가하기 전에 사용자와 합의하고, 파서에서만 처리하지 말고 AST 및 실행 모델까지 함께 반영한다.

## 현재 구현 상태

- 구현된 기반: 소스 위치와 진단 자료형, 문법 독립 AST, 스택 바이트코드, AST-to-bytecode compiler, VM 실행 루프, 동적 값·환경·함수·클래스·인스턴스·메서드 디스패치, 계산기 lexer/parser와 REPL 진입점.
- 표면 문법은 아직 산술식만 파싱한다. 함수·클래스·제어문 AST와 VM 명령은 준비되어 있지만, 그 Novi 문법은 사용자가 결정한 뒤 parser에 연결한다.
- 남은 기반: resolver/semantic analyzer, 정적 타입 검사, 별도 NIR 계층, parser 복구/AST 덤프, 모듈 로더, GC.
- 함수가 캡처한 환경은 VM 수명 동안 보유해 클로저 순환 참조를 막는다. 인스턴스 필드 사이의 순환 참조는 아직 회수하지 않으므로 추적형 GC 전까지 장기 실행 프로그램에서 메모리가 늘 수 있다.
- 빌드 검증은 C++ 표준 라이브러리 헤더와 CMake가 설치된 환경에서 해야 한다.

## 설계 원칙

- 전처리, 파싱, 의미 분석, 컴파일, 실행을 독립된 단계와 모듈로 나눈다.
- 파서는 소스 문법을 AST로 변환하고, 백엔드는 문법 표기와 직접 결합하지 않는다.
- 진단에는 파일, 줄, 열, 원문 위치를 포함한다.
- 컴파일 오류와 런타임 오류를 구분하고, 사용자에게 Novi 코드 위치를 보여준다.
- 객체·함수·모듈의 수명과 소유권은 명시적으로 관리한다. C++ raw pointer를 소유권 표현에 사용하지 않는다.
- 기능을 넣을 때마다 작은 단위로 구현하고, 단계별 동작을 검증한다.
- 외부 런타임 의존성은 초기 버전에서 최소화한다.

## 권장 처리 구조

```text
소스 파일
  → Lexer: 토큰과 소스 위치
  → Parser: AST 구성
  → Resolver / Semantic Analyzer: 이름·스코프·타입·클래스 관계 검사
  → NIR: 문법과 실행 엔진 사이의 안정된 중간 표현
  → Bytecode Compiler
  → Novi VM / Interpreter
  → 표준 라이브러리 및 런타임
```

`Interpreter`는 컴파일된 Novi 바이트코드를 실행하는 VM을 뜻한다. 초기에 AST를 직접 순회하는 임시 실행기를 만들 수는 있지만, 최종 실행 경로는 바이트코드 VM으로 통일한다. 이 구조는 소스 문법과 런타임을 분리하고, 이후 최적화나 디버깅 기능을 추가하기 쉽다.

## 백엔드 구성 요소

### 1. 프런트엔드 경계

- `SourceFile`: 소스 문자열, 파일명, 줄 시작 오프셋을 보유한다.
- `SourceSpan`: 시작·끝 위치를 보유한다.
- `Token`과 `Lexer`: 토큰 종류, 텍스트 또는 값, 위치를 제공한다.
- `Parser`: 사용자와 합의한 문법을 AST로 변환한다.
- `Diagnostic`: 오류·경고 코드, 메시지, 위치, 관련 위치를 표현한다.

### 2. AST와 의미 분석

- 표현식, 선언, 문장, 함수, 클래스, 필드, 메서드 등 개념별 AST 노드를 둔다.
- AST 노드마다 소스 위치를 보존한다.
- `Resolver`가 이름 조회, 스코프, 클로저 캡처, 상속 관계를 검사한다.
- `SemanticAnalyzer`가 타입 규칙, 접근 제한, 오버라이드 규칙 등을 검사한다.
- 타입 표기와 타입 시스템은 사용자 문법 결정 이후 추가한다. 초기에는 동적 타입을 허용하되, 정적 분석 계층을 제거하지 않는다.

### 3. 중간 표현과 컴파일러

- `NIR`은 AST에서 실행 엔진으로 내려가는 문법 독립 중간 표현이다.
- `BytecodeCompiler`는 함수별 바이트코드, 상수 풀, 디버그 위치 테이블을 생성한다.
- 제어 흐름은 점프 명령으로 표현하고, 함수 호출은 명시적 호출 프레임으로 처리한다.
- 초기 바이트코드는 단순한 스택 기반으로 설계한다. 레지스터 VM 최적화는 실제 성능 근거가 생긴 뒤 검토한다.
- 컴파일 단계는 오류가 있으면 실행 가능한 모듈을 만들지 않는다.

### 4. 객체지향 런타임

- `Value`는 초기에는 `std::variant` 기반 태그 값으로 표현한다. 숫자, 불리언, 문자열, null, 함수, 클래스, 인스턴스 등 Novi 의미에 필요한 값만 둔다.
- 객체 데이터는 `Object` 계층 또는 구분된 힙 객체로 표현하고, 객체 종류별 동작은 작은 런타임 타입에 위임한다.
- 인스턴스의 필드와 클래스의 메서드/부모 클래스 메타데이터를 분리한다.
- 메서드 호출 시 수신 객체(`this` 등 사용자가 정한 표기)를 명시적인 지역 슬롯/호출 프레임으로 전달한다.
- 상속, 메서드 디스패치, 생성자, 접근 제한, 정적 멤버의 세부 의미는 사용자 결정 후 구현한다.
- 객체 수명은 초기에 RAII와 명시적 소유권으로 단순하게 유지한다. 순환 참조, 장기 실행, 자유로운 객체 그래프가 요구될 때 추적형 GC를 도입한다. GC 전에는 `shared_ptr`를 무차별 적용하지 않는다.

### 5. VM과 호출 프레임

- VM은 바이트코드 실행 상태, 값 스택, 호출 프레임, 전역/모듈 환경을 소유한다.
- 호출 프레임에는 함수, 명령 위치, 로컬 슬롯, 클로저 환경 참조를 둔다.
- 함수 호출과 반환, 조건 분기, 변수 로드·저장, 객체 필드 접근, 메서드 호출을 바이트코드 명령으로 제공한다.
- 런타임 오류는 호출 프레임을 거슬러 올라가 Novi 소스 위치가 포함된 스택 추적을 만든다.
- VM 구현에서 바이트코드 명령 디코딩과 실행 루프를 분리해 이후 계측과 최적화를 가능하게 한다.

### 6. 모듈과 표준 라이브러리

- 사용자 문법이 정해지기 전에는 import 표기를 확정하지 않는다.
- 런타임 내장 기능과 표준 라이브러리 함수를 구분한다.
- 표준 라이브러리는 백엔드 내부 구현에 직접 박아 넣지 않고, 명시적인 모듈/함수 등록 인터페이스로 연결한다.
- 파일·프로세스·네트워크 접근 같은 외부 효과 기능은 나중에 권한과 오류 모델을 정한 뒤 추가한다.

## 구현 단계

### 단계 0 — 현재 프로젝트 확인

- [ ] 기존 계산기 코드와 실행 환경을 확인한다.
- [ ] `src/main.cpp`가 비어 있으면 기존 계산기 설명과 실제 상태를 맞춘다.
- [ ] C++ 표준, 빌드 명령, 진입점, 오류 출력 형식을 기록한다.
- [ ] 아주 작은 수동 실행 예시를 정한다.

### 단계 1 — 소스 모델과 진단

- [ ] `SourceFile`, `SourceSpan`, `Diagnostic`을 구현한다.
- [ ] 줄·열 계산과 여러 오류 출력 형식을 마련한다.

### 단계 2 — Lexer와 Parser

- [ ] 사용자가 합의한 표기만 토큰/문법으로 추가한다.
- [ ] AST 노드와 파서 오류 복구를 구현한다.
- [ ] AST 출력기 또는 덤프 모드를 만들어 파싱 결과를 확인할 수 있게 한다.

### 단계 3 — 이름 해석과 객체 의미

- [ ] 스코프 및 심볼 테이블을 구현한다.
- [ ] 함수, 클래스, 필드, 메서드의 선언과 참조 검사를 추가한다.
- [ ] 상속·오버라이드·접근 제어는 사용자가 정한 규칙에 맞춰 추가한다.

### 단계 4 — NIR와 바이트코드

- [ ] AST를 NIR로 내린다.
- [ ] NIR 검증 및 바이트코드 생성을 구현한다.
- [ ] 소스 위치 테이블을 보존해 실행 오류와 연결한다.

### 단계 5 — VM과 객체 런타임

- [ ] 값 스택과 호출 프레임을 구현한다.
- [ ] 기본 값, 변수, 함수 호출을 실행한다.
- [ ] 클래스, 인스턴스, 필드, 메서드 디스패치를 추가한다.
- [ ] 런타임 오류와 Novi 스택 추적을 제공한다.

### 단계 6 — 모듈·라이브러리·성능

- [ ] 사용자 문법 결정 후 모듈 로딩을 연결한다.
- [ ] 표준 라이브러리 등록 API를 마련한다.
- [ ] 실제 프로그램으로 프로파일링한 뒤 병목에 한해 최적화한다.
- [ ] GC, 바이트코드 캐시, JIT는 요구와 측정이 생긴 경우에만 별도 설계한다.

## 언어 기능 조사 방법

Java, Kotlin, C++, Go, Python, JavaScript, TypeScript의 “모든 라이브러리”를 한 번에 복사하거나 완전 목록으로 나열하는 것은 범위가 너무 크고 버전마다 달라진다. 공식 문서를 기준으로 **언어 문법**, **표준 라이브러리**, **런타임/도구**를 분리한 비교표를 만든다. 외부 패키지 생태계는 표준 라이브러리와 따로 기록한다.

기능 비교표 열 예시:

| 항목 | 출처 언어 | 분류 | Novi에 필요한 이유 | 문법/의미 결정 | 백엔드 지원 | 우선순위 |
|---|---|---|---|---|---|---|
| 클래스·인스턴스 | Java/Kotlin 등 | 객체 모델 | 사용자 정의 타입·상태 표현 | 미정 | 미구현 | 1차 |

조사할 범주:

- 값과 타입, 변수·상수, 연산자, 변환
- 함수, 기본 인자, 오버로딩, 클로저, 제너레이터
- 클래스, 인터페이스/트레이트, 상속, 프로퍼티, 제네릭
- 조건·반복·패턴 매칭, 예외/오류값
- 배열·맵·집합·문자열·날짜·수학·파일·네트워크
- 모듈, 패키지, 빌드 도구, 패키지 관리자
- 메모리 관리, 동시성, 비동기 작업
- 매크로/전처리, 리플렉션, FFI, 디버깅·프로파일링

조사할 때 문서에 나온 기능을 무조건 Novi에 넣지 않는다. 먼저 사용 사례와 의미를 비교하고, 중복되거나 구현 비용이 큰 기능은 보류한다. 타 언어의 이름과 문법을 복사하기보다 Novi의 규칙을 새로 정한다.

## 역할 분담

- **사용자:** Novi가 제공할 기능과 표기, 사용 예시, 의미 규칙을 제안하고 결정한다.
- **구현 담당(C++):** 합의된 기능을 lexer/parser 경계, 의미 분석, NIR, 바이트코드, VM, 런타임에 연결하고 진단을 구현한다.
- 구현 단계에 들어가기 전 각 기능에 대해 짧은 예시와 기대 결과를 합의한다.

## 완료 기준

- 문법 표기를 바꾸더라도 VM 및 객체 런타임을 다시 작성할 필요가 없다.
- 클래스와 인스턴스 관련 오류가 잘못된 구문 위치와 함께 표시된다.
- 파싱 오류, 의미 오류, 컴파일 오류, 런타임 오류가 구분된다.
- 컴파일러와 VM의 각 경계를 독립적으로 확인할 수 있다.
- 큰 라이브러리나 언어 기능을 무계획하게 복사하지 않고, 조사 근거와 Novi 채택 결정을 추적할 수 있다.
